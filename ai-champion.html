Skill 01

generate-ds-ui

Screens built only from components that actually exist.

A design system is only worth what people actually build with it — and a library of a few hundred components is genuinely hard to reach. Designers know it best and still lose time checking which variant is current before starting a screen. Everyone else is further away again. The distance between "we have a design system" and "this screen uses it" is exactly where consistency leaks, quietly, one file at a time.

This skill closes that distance by making the system reachable instead of memorable. It fetches the live inventory itself and refuses to output anything it cannot trace back to a real component — so a designer gets a consistent, on-system starting point without auditing it by hand, and someone in product can produce something genuinely buildable without knowing the library at all.

It has two output modes. Code produces a live prototype from the token file — good for feeling an interaction. Figma places real component instances in a real file, where fidelity is guaranteed by construction: an instance of a real component physically cannot have the wrong padding. Same brief, same pipeline, two deliverables depending on whether you need to click it or review it.

Product Design

Consistency by default

The main use. Start from a screen that is already on-system, so review is about the idea rather than about which button variant this is and whether the spacing is ours.

Product

A real starting point

A PM can put a concrete, buildable screen into a conversation instead of a wireframe that has to be redrawn — without learning the component inventory first.

Engineering

Nothing to translate

What arrives is composed of components that already exist, with real tokens — so the handoff conversation is about behaviour, not about what half of it should have been.

Problem

Ask any AI for a settings page and you get one — with invented components, hardcoded spacing and a button variant we never shipped. It looks plausible in a screenshot and falls apart the moment a developer opens it. Meanwhile the real system sits there, correct and underused.

The need

Anyone shaping a screen — designer, PM or developer — should land on something already design-system-correct: consistent for the design team by default, and reachable for everyone else without knowing the inventory.

Solution

Sync the live component inventory before every run, compose only real components with measured tokens, then verify the output against that same data — and fail the run if anything was invented.

    Skill 02

    generate-misc-icon

    New brand icons that read as siblings, not cousins.

    Our spot icons are a real graphical language: indigo outlines with round joins, white and lavender fills, exactly one lime focal, and a recurring four-point sparkle whenever something is AI-driven. Those rules are easy to state and surprisingly hard to hit. A generic AI gets close enough to be tempting and wrong enough to be unusable — the stroke is a third of a pixel heavy, the lime lands in two places, the ink is a hex nobody uses.

    The fix was to stop describing the style and start measuring it. Every run re-imports the real icon folder and derives the palette, stroke weight and canvas from the actual files, so the skill is always calibrated to the set as it exists today — not as it looked when the instructions were written. Then it proves the result: rendered at the sizes it ships at, placed beside a real icon, and refined until the differences are gone.

    Problem

    Every new spot icon drifts. Drawn from memory it misses the stroke weight, the exact ink, the lavender-and-one-lime rule, the sparkle convention — and then blurs into mush at the size it actually ships at.

    The need

    Icons that belong to the existing set on first delivery, proven legible at the two real header sizes — 48px and 38px — before anyone opens Figma.

    Solution

    Learn from the real icon set every single run, draw to canonical tokens, then render at ship sizes and compare side by side with a real icon — looping until the deltas are gone.

    The shape of it

    Four steps in, a loop, then out

    Sync, study and metaphor all happen before a single line is drawn — that is the part people skip, and it is why most generated icons are wrong before they exist.

    Then the middle three run as a cycle, not a sequence. Render it, put it beside a real icon, name the deltas, fix them, render again. The skill stays in that loop until the differences are gone — which is the whole reason the output ends up looking like it belongs.

      Skill 03

      ux-test-analysis

      Research that compounds instead of evaporating.

      Running the session is the fun part. What comes after it is the part that quietly destroys a designer's month — and it is the reason so much research is never actually analysed.

      Done properly by hand, one round of testing is days of work: re-watching every recording, timestamping the moments that mattered, tagging each task as completed, helped, partial or failed, pulling and attributing quotes, clustering fifty scattered observations into a handful of real issues, arguing about severity, checking whether each one already appeared in an earlier test, writing recommendations, prioritising them, and finally rebuilding it all into a deck. Multiply that by five participants and every feature the team ships, and analysis becomes the thing that gets postponed — until the insight is stale and someone asks "didn't we already test this?" and nobody can answer.

      By hand, per round 3–5 days

      1. Re-watch every session and timestamp what mattered
      2. Clean the transcript and label who said what
      3. Tag each task: completed · helped · partial · failed
      4. Pull quotes and attribute them without exposing anyone
      5. Cluster scattered observations into distinct issues
      6. Decide severity — then defend it in a review
      7. Check every issue against previous tests by memory
      8. Write recommendations and prioritise them
      9. Rebuild the whole thing as a deck
      10. Share it once. Never query it again.

      And the output is a static document. Nothing about it makes the next test cheaper.

      With the skill ~15 min

      1. Drop in the transcript
      2. Confirm the feature name it suggests
      3. Read the result and correct anything it got wrong

      The output is a live workspace — structured, searchable, and comparable with every test that came before it. The next round starts ahead, not from zero.

      Problem

      Usability tests end as a transcript and a deck. Findings live in whoever ran the session; nothing is queryable, nothing accumulates, and the same issue gets rediscovered a quarter later.

      The need

      Evidence you can search, scores you can compare across tests, and a way to check a design assumption against what the team already learned — before building on it.

      Solution

      Turn a raw transcript into a structured Notion workspace — sessions, issues, recommendations, participants, quotes — with a computed UX Health Score, an analysis page, and dated notes pinned onto the Figma designs.

      "Any LLM can summarise a transcript"

      True — and that is exactly the trap. Paste a transcript into any chat and you will get a confident, readable summary in seconds. It feels like the job is done. It is not, and the difference only shows up months later when you need the research again.

      A summary is prose about one session. It lives in a chat window, it is shaped slightly differently every time you ask, it will happily invent a difficulty rating that was never given, and it cannot be filtered, counted or compared. This skill produces something else entirely:

      Data, not prose

      Rows you can query

      Six linked databases instead of paragraphs — issues, sessions, quotes, recommendations, participants. You can filter by severity, count recurrences, and sort by impact. A summary cannot be sorted.

      Same shape, every time

      Comparable by construction

      Identical schema, identical severity logic, identical scoring formula on run one and run fifty. An ad-hoc prompt gives a differently-shaped answer each time, which is why chat summaries can never be compared to each other.

      It accumulates

      Recurring issues gain weight

      An issue seen before does not become a second document — it gains new evidence on the existing record, and its severity rises as it keeps happening. That is a pattern you can act on, not five separate reports saying the same thing.

      It refuses to fill gaps

      Missing stays missing

      If a rating was never collected, it is marked not captured — never estimated into something plausible. Invented research is worse than none, because it is indistinguishable from the real thing later.

      Safe to keep

      Anonymised by rule

      Nothing identifying is stored — not the client, not the participants. Findings are indexed by feature, product area and date instead, so the whole archive can be shared across the team without a privacy review each time.

      It answers back

      Evidence Check

      State an assumption — "users understand the CSV export" — and it searches every test ever run, then answers supports, contradicts, mixed or insufficient evidence, with sources. A chat summary cannot be interrogated a year later.

        Why the quotes matter most

        A success rate tells you that something went wrong. It cannot tell you what the person was thinking when it did — and that is the only part a team can actually design against. "Export scored 41%" starts an argument. "I don't know if I'm getting what I filtered or everything" ends it, because everyone in the room instantly understands the confusion and can picture the fix.

        So quotes are treated as first-class evidence, not decoration: captured verbatim, linked to the issue and the mission they came from, and deliberately kept in both directions — the friction and the moments something clearly worked. A report with only complaints is as misleading as one with none.

        The part that changed how we work is what happens when the same sentence comes back. One person saying it is an anecdote. The same confusion, from a different person, at a different company, months later, is a finding — and it is exactly the pattern a human reading four separate decks would never spot. Because every quote is stored as data against a feature, the skill matches recurrences across the whole archive and marks them: ↻ heard in 4 of 4 tests. That badge is what turns a nagging suspicion into a prioritised ticket.

        Two dashboards, not one

        Each test gets its own analysis page — the one above. But a single test is a snapshot, and features are not judged on snapshots. So every test also rolls up into a feature-level dashboard that watches all of them together, recalculating from the raw data each time rather than averaging the averages.

        The score became the release gate

        The searchable archive is the obvious win. The unexpected one was the score.

        Because it is computed the same way on every test — half task success, a quarter self-rated difficulty, a quarter issue severity — one round is directly comparable to the last. That turned a subjective conversation into a shared one. "I feel like people struggled with export" became "task success on export was 41% with two criticals open, and the feature scores 72." A designer, a PM and a developer can all act on the second sentence.

        So it quietly became our answer to the hardest question in the process — is this ready to hand to development? Not a rule anyone imposed; a number everyone started asking for, because it is the same number every time and the calculation is always shown, so it can be argued with. An unauditable score is just an opinion with a number attached.

        80 — 100

        Healthy

        Hand it over. Log the low-severity issues as follow-ups rather than blockers.

        65 — 79

        Ship it, but fix the flagged issues first. This is where most features land on the first round.

        45 — 64

        At risk

        Something structural is wrong. Rework the flow and retest before writing a single ticket.

        Below 45

        Critical

        Do not hand this to development. Building it now means building it twice.

        One honest caveat the skill enforces itself: research confidence is tracked separately from the score. Five participants on one prototype is not the same evidence as four rounds across real customers, and the report says so out loud rather than letting a clean number imply certainty it has not earned.

        Nothing identifying goes in. Not the client, not the participants, not a single email address — the workspace holds behaviour and evidence, never people or accounts. Research stays findable through the feature, the product area and the date, which is how anyone actually searches for it later anyway.

        Dolly at work — the same Claude, running with memory, tooling and a permission model.

        Separate personal project

        Dolly — a personal design OS

        Dolly is not one of the skills, and it does not depend on them. It is the environment I work in: a Senior Product Designer agent running on Claude Code, built as a personal operating system rather than a tool with a fixed job.

        It is not a different model, and not a smarter one. It is the same Claude, wrapped in a working layer that gives it a role, a memory that survives between sessions, real tooling, and rules about what it may touch without asking. Claude is the reasoning. Dolly is the reasoning plus memory, a specialism, tools, and a permission model.

        Nine differences, and none of them are about intelligence.

        How a session runs

        Five steps and one gate. Reading is free; changing anything real waits for a yes.

        ↺ The return arrow is the whole point. What was worth keeping is written back before the session ends — so the next one starts where this one finished, not from scratch. Everything else is a nicer interface; this loop is what makes tomorrow better than today.

        The vault is just Markdown

        There is no database behind any of this. The vault is an Obsidian-compatible folder of plain Markdown files sitting on disk — projects, decisions, preferences and history, each one a file you could open in any text editor. Dolly reads and writes them directly through Claude Code.

        Obsidian is the human end of it: somewhere to browse the vault, edit a page by hand, and see the links between notes as a graph — which is exactly the picture above. But it is an interface, not a dependency. Close Obsidian and Dolly carries on, because the files never needed it.

        Three memory layers

        Each layer has one job, and a fact lives in exactly one of them — writing the same thing twice is how two copies start quietly contradicting each other.

        Built to grow, and to be someone else's

        Nothing about Dolly is finished, and that is the design. It is a shape you extend rather than a product you use — the knowledge base is deliberately empty in the repo, so anyone who forks it fills it with their own people, projects and decisions and ends up with a different assistant that behaves like theirs.

        The privacy line is drawn in the same spirit: the vault is local-only and kept out of git by an allowlist, because it holds named colleagues, customer accounts and meeting transcripts. The repo is the shape of the system. What it knows stays on my machine.

        When a plain chat is the better tool

        Anything that does not need your history — a generic question, a quick explanation, throwaway code, a topic unrelated to the day job. Loading project context costs tokens and adds nothing there. Dolly earns its keep on work that is continuous, opinionated and design-system-bound; pretending it wins everywhere would just make it slower at the easy things.

        Build the system, not the output.

        A good prompt makes one good screen. A skill makes every screen after it correct by default, and anyone on the team can run it without knowing what I know. An OS goes further — it remembers why, so the next question starts from everything already settled. Both are the same bet: spend the effort once, upstream, where it keeps paying.
